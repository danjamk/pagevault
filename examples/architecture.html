pagevault architecture

The architecture, in two moves

You publish from anywhere. Your client opens exactly what they’re allowed to.

Both halves are one Cloudflare Worker on a single hostname. This page walks the operator’s side first — how the collection gets made — then the viewer’s side — how it stays locked down.

Many clients, one Worker

Whatever you make an artifact in, publishing it is the same call to the same Worker — which is why the CLI and the remote MCP server are thin clients, not separate backends.

The console (/admin) is the only operator path behind Cloudflare Access; /mcp and /api carry a bearer token the Worker checks itself.

Act 2 · the viewer

This is how it secures what your client opens

A document is LLM-generated and assumed hostile, and it may be a client’s confidential report. Three gates stand between a link and the bytes — identity, authorization, isolation.

01

Identity

“who are you?”

Zero Trust Access signs the visitor in at the edge and hands the Worker a signed token — which the Worker verifies itself, trusting no cookie. People who come back get a seat; people who read once get a capability link that needs no login and costs nothing.

02

Authorization

“may you see this?”

One pure function — canView() — decides every read, with no exceptions (the MCP read tools go through it too). Pick a viewer and a document and watch the exact line that decides fire.

Isolation
“and it never runs as us”

        
Even allowed, the artifact renders in a sandboxed frame with an opaque origin. Scripts run; reading our cookies or DOM does not.
